## Architectural rule (applied uniformly)

- **Own-feature access**: a use case depends on its feature's **concrete** service (e.g. `EmployeeService`), which is the sole gateway to that feature's `*RepositoryPort`. **No own-service port.**
- **Cross-feature access**: the **consumer** declares a narrow `Protocol` port in its own `application/ports.py` with only the methods it needs. The provider ships only the concrete service, which satisfies the consumer's port structurally. **The provider never defines a service port for other features.**
- **Invariant**: no `use_cases.py` imports any `*RepositoryPort`. Repository ports are imported only by (a) their own feature's concrete service and (b) the SQL repository implementation.
- **Commands**: all commands across all features carry `current_user: CurrentUser`.
- The legacy free functions (`get_owned_business`, `get_owned_employee`, `get_owned_transaction`, `get_existing_holiday`) are **deleted** — their logic moves into services / use-case orchestration.

Resulting port inventory:
- `business/application/ports.py` → `BusinessRepositoryPort` only (no service port).
- `employee/application/ports.py` → `EmployeeRepositoryPort` + consumer `BusinessServicePort` (`get_owned_business`).
- `holiday/application/ports.py` → `HolidaysRepositoryPort` + consumer `BusinessServicePort` (`get_owned_business`).
- `transaction/application/ports.py` → `TransactionRepositoryPort` + consumer `BusinessServicePort` (`get_owned_business`) + consumer `EmployeeServicePort` (`get_owned_employee`).
