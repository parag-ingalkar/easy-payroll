# Plan: Integrate the Next.js frontend with the FastAPI backend

## Goal
Rewire the existing `frontend/` (a Prisma+SQLite standalone SPA) so it talks to the FastAPI backend at `localhost:8000`, and extend the backend with the few features the frontend currently has but the backend lacks. Reuse all existing views, components, and the design system; change only the data layer and the small set of features that need backend additions.

## Confirmed decisions
- **Modify `frontend/` in place** (keep all views/components/styling; replace the data layer).
- **Connectivity via Next.js rewrites** — proxy `/api/*` → `http://localhost:8000/api/*`. Makes everything same-origin, so the refresh cookie (`samesite=lax`, `path=/api/auth`) works as-is with no backend cookie/CORS changes.
- **snake_case ↔ camelCase adaptation in the API client** — frontend types stay camelCase; a small transform layer (camelcase-keys/snakecase-keys) converts at the fetch boundary. Views untouched.
- **Transactions: two types only** — keep backend `addition`/`deduction`; the frontend money tab will offer Addition/Deduction only (drop advance/bonus).
- **Owner-only auth** — skip employee self-service login and the invite flow for now. Remove the `employee-app-view`, `accept-invite-view`, and invite generation from the frontend.
- **Mark-paid included** — extend payroll with a `paid` status, payment method, and mark-paid / mark-all-paid endpoints.

## Part A — Backend extensions

Each addition follows the existing hexagonal/vertical-slice conventions (domain → application → infrastructure → presentation). Every write use case uses the existing `SQLAlchemyUnitOfWork`. All routes mount via `app/core/router.py`. New columns/migrations use Alembic autogenerate. Lint gate: `cd backend && uv run ruff check && uv run ruff format --check && uv run pyright`.

### A1. CORS + ping (small but required)
Even with the Next proxy, add a minimal `CORSMiddleware` to `backend/app/main.py` using `get_settings().frontend_url` (read the existing-but-unused config value), `allow_credentials=True`, all methods/headers — defensive for any direct-call or tooling scenario. Update `frontend_url` default to `http://localhost:3000` in `config.py`.

### A2. Payroll mark-paid (new lifecycle state + endpoints)
Extend the payroll feature to support per-line-item payment.

- **Domain** (`payroll/domain/value_objects.py`): add `PAID = "paid"` to `PayrollStatus`. Add a new value object `PaymentMethod(StrEnum) { CASH="cash", UPI="upi", BANK="bank" }`.
- **Domain entity** (`payroll/domain/entities.py`):
  - `PayrollLineItem`: add `mark_paid(method, date)` method that sets `status=PAID`, `paid_via=method`, `paid_date=date`. Guard: only allow from `DRAFT`/`FINALIZED` (reject if already paid → new `PayrollAlreadyPaidError(ConflictError)` in `exceptions.py`).
  - `PayrollRun`: add a read-only `is_paid` roll-up concept (computed: all line items paid) — surfaced only in the response, not stored. Add `mark_all_paid` helper on the run that delegates to each line item.
- **Application**:
  - `commands.py`: `MarkLineItemPaidCommand(current_user, business_id, payroll_id, line_item_id, paid_via, paid_date?)`, `MarkAllPaidCommand(current_user, business_id, payroll_id, paid_via, paid_date?)`.
  - `ports.py`: add `get_line_item_by_id_or_raise`, `update_line_item` to `PayrollRepositoryPort` (and to `PayrollService`).
  - `use_cases.py`: `MarkLineItemPaidUseCase` (verify ownership → get run → get line item → `mark_paid` → update) and `MarkAllPaidUseCase` (get all line items → mark each → bulk update). Both wrap in `uow`.
- **Presentation**:
  - `schemas.py`: add `MarkPaidRequest{paid_via: PaymentMethod, paid_date?: date}`; `PayrollLineItemResponse` already has `status/paid_via/paid_date`. Add `is_paid: bool` to `PayrollRunResponse`.
  - `routes.py`: two new endpoints (both return full `PayrollRunResponse` with nested items, mirroring `get_payroll_run`):
    - `PATCH /business/{business_id}/payroll/{payroll_id}/line-items/{line_item_id}/pay`
    - `PATCH /business/{business_id}/payroll/{payroll_id}/pay-all`
  - `dependencies.py`: wire the two new use cases.
- **Migration**: `payroll_status_enum` gains `paid`. Autogenerate will produce an `ALTER TYPE ... ADD VALUE 'paid'`. Review + `uv run alembic upgrade head`.

### A3. Dashboard aggregate endpoint
A single read endpoint to power the owner dashboard, avoiding N+1 round-trips from the client.

- **New mini-feature** `app/features/dashboard/` (presentation-only; no model of its own — reads across business/employee/attendance/payroll/holiday via existing services):
  - `presentation/schemas.py`: `DashboardResponse` with `{ thisMonthPayroll: {status, totalAmountDue, isWarning, payrollId?}, todayAttendance: {present, halfDay, paidLeave, unpaidLeave, absent, totalEmployees}, monthlyFinances: {totalAdditions, totalDeductions}, attendanceTrend: [{date, presentCount}...] (last 7 days), payrollHistory: [{month, year, totalAmountDue, status}...] (last 6 months), employeeCount, activeRunExists }`.
  - `presentation/routes.py`: `GET /business/{business_id}/dashboard` (Bearer auth + ownership via `business_service.get_owned_business`). Mount in `core/router.py` at `/business/{business_id}/dashboard`, tag `dashboard`.
  - `presentation/dependencies.py`: wire `BusinessService`, `EmployeeService`, `AttendanceService`, `HolidayService`, `PayrollService`.
  - Use a thin application service (in `application/services.py` or a `use_cases.py`) to assemble the payload, reusing existing service methods (e.g. `payroll_service.get_by_business_and_period`, `attendance_service.list_by_business_and_date`, `employee_service.list_by_business`). Currency formatting stays client-side.

### A4. Business fields: `state` + `currency`
The frontend onboarding/settings uses `state` and `currency`; the backend `Business` has neither.

- **Business domain entity** (`business/domain/entities.py`): add `state: str | None`, `currency: str` (default `"INR"`).
- **Infrastructure model** (`business/infrastructure/models.py`): add `state: Mapped[str | None]` (String(120), nullable), `currency: Mapped[str]` (String(8), default `"INR"`, server_default `"INR"`). Update `from_domain`/`to_domain`.
- **Presentation schemas** (`business/presentation/schemas.py`): add `state`, `currency` to `CreateBusinessRequest` (optional), `UpdateBusinessRequest` (optional), and `BusinessResponse`.
- **Migration**: autogenerate adds the two columns; `upgrade head`.

> (No backend changes needed for transactions-two-types or owner-only auth — those are frontend-side decisions.)

## Part B — Frontend rewire (in place)

### B1. Remove Prisma + Next API routes + dead deps
- Delete `frontend/prisma/`, `frontend/db/`, `frontend/src/lib/db.ts`, and the entire `frontend/src/app/api/` directory (all 16 route handlers).
- Remove `@prisma/client`, `prisma` from `frontend/package.json` (and the `db:*` scripts). Prune unused deps if desired (next-auth, next-intl, framer-motion, @dnd-kit/*, @mdxeditor/editor, z-ai-web-dev-sdk) — optional cleanup, not required.
- Delete `frontend/.env` (the leftover Prisma `DATABASE_URL`).

### B2. Configure the proxy + env
- `frontend/next.config.ts`: add `rewrites()` returning `[{ source: "/api/:path*", destination: "${process.env.BACKEND_URL || "http://localhost:8000"}/api/:path*" }]`.
- New `frontend/.env.local`: `BACKEND_URL=http://localhost:8000`. (Server-side rewrite; no `NEXT_PUBLIC_` needed.)
- Because requests are same-origin (proxied), the backend's refresh cookie applies automatically; `credentials: "include"` still set on fetch for correctness.

### B3. Rewrite the API client + auth (`src/lib/api.ts`, `src/lib/auth-context.tsx`)
This is the heart of the integration. Replace the Prisma-coupled fetch logic with a FastAPI-aware client.

- **`src/lib/api.ts`** — new typed client:
  - Central `BACKEND_URL` not needed (proxy makes calls same-origin `/api/...`).
  - `apiFetch<T>(path, options)`: attaches `Authorization: Bearer <accessToken>` from an in-memory token store, sets `credentials: "include"`, JSON headers.
  - **Automatic token refresh**: on a 401 with `code === "invalid_access_token"`, call `POST /api/auth/refresh` once (cookie-sent), store the new access token, and retry the original request. If refresh fails (`invalid_token`), clear auth and redirect to login.
  - **snake↔camel transform**: import `camelcase-keys` / `snakecase-keys`. Outgoing JSON bodies are converted to snake_case; responses are converted to camelCase (depth-limited). This lets all existing `*Shape` camelCase types and views stay unchanged.
  - **Error normalization**: backend errors are `{detail, code}`; throw an `ApiError` carrying both so callers/toasts can use `detail`. Drop the old `{success,data}` envelope handling.
- **Access-token store**: a small module (e.g. `src/lib/token-store.ts`) holding the in-memory access token + expiry (`expires_in`), with get/set/clear. Kept in memory only (not localStorage) for security; refresh cookie persists across reloads.
- **`src/lib/auth-context.tsx`** — rework `AuthProvider`:
  - On mount: call `POST /api/auth/refresh` (cookie) to silently restore a session; if it returns a token, hydrate via `GET /api/users/me`. If refresh fails, user is logged out (no error toast).
  - `login(email, password)` → `POST /api/auth/login`, store access token, set `user` from `/api/users/me`.
  - `register(name, email, password)` → `POST /api/auth/register`, then auto-login.
  - `logout()` → `POST /api/auth/logout` (cookie), clear token store + state.
  - Replace phone-based fields with **email** (login/register forms updated in B5).
  - Expose `{ user, loading, login, register, logout, refreshUser }`. Drop `business`, `employee`, `acceptInvite` (business is fetched separately via React Query; employee removed — owner-only).
  - `useAuth().user` shape: `{ id, email, name, roles }` (matches `UserResponse`).

### B4. Update `src/lib/types.ts` to match backend shapes (camelCase)
Field-by-field reconciliation so the transform layer yields exactly these:
- `SessionShape` → `{ id, email, name, roles: string[] }` (replace `phone`/`role`).
- `BusinessShape` → add `slug`, `currency`; keep `state`. Drop nothing. `divisorPolicy`/`defaultWeeklyOffDays` arrive as string/array — `weeklyOffDays` will be `string[]` (backend `ARRAY(weekday)`); update type from `string` to `string[]` and adapt the few consumers (toggle-group multi-selects) accordingly.
- `EmployeeShape` → `userId` removed (no user link); `phone` optional (already nullable). `weeklyOffDays` → `string[]`.
- `TransactionShape` → `type: "addition" | "deduction"`; `note` → `description`; `transactionDate` stays.
- `AttendanceShape` → `notes` removed (backend has none); `date` stays.
- `HolidayShape` → `date` → `holidayDate`; add `holidayType`.
- `PayrollRunShape` → add `totalAmountDue`, `isWarning`, `isPaid`. `lineItems` nested.
- `PayrollLineItemShape` → expand to backend's full set (`divisorPolicyUsed`, `weeklyOffDaysCount`, `totalAdditions`/`totalDeductions` instead of `totalBonuses`/`totalAdvances`). Drop `totalBonuses`/`totalAdvances`.
- `ApiResult<T>` → remove (no envelope).

### B5. Update views & query/mutation calls
For each view, swap its `apiFetch("/api/...")` calls for the backend paths below. Most view code stays; only URLs, request bodies, and a few field names change.

Endpoint map the views will call (all Bearer-auth, same-origin via proxy, responses camelCased):
- **Auth**: `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `POST /api/auth/refresh` (client-internal), `GET /api/users/me`.
- **Business**: `POST /api/business`, `GET /api/business`, `GET /api/business/{id}`, `PATCH /api/business/{id}`. (Onboarding creates; settings edits; store the single business id after login.)
- **Dashboard**: `GET /api/business/{businessId}/dashboard`.
- **Employees**: `POST /api/business/{businessId}/employees`, `GET /api/business/{businessId}/employees?include_inactive=true`, `GET /api/employees/{id}`, `PATCH /api/employees/{id}`, `DELETE /api/employees/{id}` (hard delete — backend has no soft-delete; this is acceptable, or use `PATCH .../deactivate`). Activate/deactivate available if we want soft-delete semantics.
- **Attendance**: `GET /api/business/{businessId}/attendances/by-date/{date}`, `PUT /api/business/{businessId}/attendances/bulk?attendance_date={date}` (mark-all-present + per-row upserts), `GET /api/business/{businessId}/employees/{employeeId}/attendances?year=&month=`.
- **Transactions**: `GET/POST /api/business/{businessId}/employees/{employeeId}/transactions`, `PATCH/DELETE .../transactions/{id}`. Type selector → Addition/Deduction only; field `description` (was `note`).
- **Holidays**: `GET/POST /api/business/{businessId}/holidays`, `DELETE .../holidays/{holidayDate}` (delete by date, not id — adjust the UI delete call).
- **Payroll**: `POST /api/business/{businessId}/payroll`, `GET /api/business/{businessId}/payroll`, `GET .../payroll/{id}`, `PATCH .../payroll/{id}/finalize`, `PATCH .../payroll/{id}/line-items/{lineItemId}/pay`, `PATCH .../payroll/{id}/pay-all`.

Specific view changes:
- `login-view.tsx` / `register-view.tsx`: switch phone → **email** (update zod schema + input). Register now sends `{ name, email, password }`.
- `onboarding-view.tsx`: create business via `POST /api/business` with `{ name, divisor_policy, default_overtime_multiplier, default_weekly_off_days, default_working_hours, state, currency }`. Build `slug` client-side (slugify name) since backend requires it, or have the backend auto-derive — **recommend backend auto-derives slug from name** (small backend tweak in A4/business use case) to avoid client slug collisions. Weekly-off multi-select now emits `string[]`.
- `settings-view.tsx`: `PATCH /api/business/{id}` for profile; holidays use new paths + `holiday_type`. Add `currency`/`state` editing.
- `dashboard-view.tsx`: replace its many `useQuery` calls with a single `useQuery(["dashboard", businessId])` → `GET .../dashboard`; map the aggregate payload to the existing cards/charts. Remove the "add demo data" seeder (no `/api/seed`) — or add a backend seed endpoint later (out of scope).
- `attendance-view.tsx`: use `by-date` GET + `PUT .../attendances/bulk` for both per-row and all-present. The bulk endpoint takes `entries: [{employee_id, status, overtime_hours?}]` + `?attendance_date=`. Overtime per-row: the bulk entry supports `overtime_hours`, so include it.
- `employees-view.tsx` + `employee-detail-view.tsx`: employee create no longer generates an invite (remove invite-link UI/copy/share). Money tab transaction type → Addition/Deduction; field `description`. Employee detail attendance tab uses the employee-scoped attendance list.
- `payroll-view.tsx` / `payroll-run-view.tsx`: run via `POST /api/payroll`; finalize via PATCH; mark-paid via the two new endpoints; payment-method picker (cash/upi/bank). Line-item breakdown uses the expanded fields. CSV export (`lib/csv-export.ts`) and slip print (`lib/slip-print.ts`) need only field-name updates to the new line-item shape.
- `app/page.tsx`: simplify the gate — splash while loading; no user → login/register; owner without business → onboarding; else AppShell + selected view. **Remove** the `inviteToken`/accept-invite branch and the `EMPLOYEE` → `EmployeeAppView` branch.
- Delete `employee-app-view.tsx` and `accept-invite-view.tsx`; remove `acceptInvite` from `useAuth` and the invite token helpers from `app-store.ts`/`page.tsx`.

## Notes / deviations (explicit)
- **Backend `DELETE /api/employees/{id}` is a hard delete** (cascade removes attendance/transactions/line items). The old frontend used soft-delete (`isActive=false`). We'll prefer `PATCH .../deactivate`/`activate` for the UI's "remove" action to preserve history, and reserve hard `DELETE` for a true destructive action. The employees list will use `?include_inactive=true` so deactivated staff can be shown/hidden.
- **`weeklyOffDays`** changes type from `string` to `string[]` in the frontend types; the multi-select ToggleGroup already returns arrays, so this is mostly a type alignment.
- **Onboarding slug**: recommend the backend auto-generates `slug` from the business name (kebab-case, suffix-on-collision within owner) so the frontend never has to. This is a small addition to the business create use case in A4.
- **No `/api/seed`**: the dashboard's "add demo data" button is removed. Seeding can be added as a dev-only backend endpoint later if wanted.
- **Auth model shift**: phone+session-cookie → email+JWT. The refresh cookie is httpOnly and same-origin (proxied), so it's never exposed to JS; the short-lived access token lives in memory only. This is a security improvement over the old `pp_session` cookie.
- **Role claims exist but aren't enforced** in the backend (all access is owner-scoped via `business.owner_id`). Since we're owner-only, this is fine; no RBAC work needed.
